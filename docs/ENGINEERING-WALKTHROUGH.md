# Engineering walkthrough

A guided reading order through the codebase, from a file of logs to a compared what-if. Each stop names the file, what to look for, and the test that pins it down.

## Map


## 1. From bytes to events

Start at `packages/engine/src/normalize/normalize.ts`, `normalizeSource`.
- Format detection, then a parser per format (`parsers.ts`). Lines that can't be read are kept as errors with line numbers. They aren't silently dropped, and the import wizard shows them.
- `fields.ts` maps the many spellings of time, level, service and trace id onto one shape.
- `redact.ts` runs before anything is stored. Secrets and email addresses are replaced.
- Ids are content hashes (`util/hash.ts`), so duplicates collapse and re-imports are idempotent.
- Limits (`maxRecords`, size) throw `ImportTooLargeError` instead of degrading.

Tests: `normalize/normalize.test.ts`, with fixtures in `packages/engine/fixtures/`. Those same files are offered as sample downloads in the import flow (`public/samples/`).

## 2. Linking events

`correlate/correlate.ts`, `correlate`.
- Candidates come from a time window plus the dependency graph (`graph/topology.ts`), not all pairs.
- Signals are weighted and combined by noisy-OR, then multiplied by `exp(-Δt/τ)`.
- Edges always point from earlier to later, so the graph is a DAG.

`correlate/hypotheses.ts`, `rankHypotheses`, turns linked events into candidate causes with evidence lists.

Tests: `correlate/correlate.test.ts`.

## 3. Scrubbing time

`replay/replay.ts`, `ReplayEngine`.
- Timestamps in a `Float64Array`. `seek(t)` binary-searches, then folds `applyEvent` forward from the nearest checkpoint (every 256 events).
- Bursty event types are rate-limited in the "important events" list with a cooldown, so a flood of errors doesn't drown out the deploy that caused them.
- `deriveHealth` turns a rolling error window into healthy, degraded, failing or recovering.

Tests: `replay/replay.test.ts`, including seek-equals-full-replay checks.

## 4. Simulating a system

`simulate/model.ts` defines services (capacity, queue, service time, timeout, retry, breaker, contention), calls and traffic. `simulate/simulator.ts`, `runSimulation`:
- A min-heap of `(t, seq)` events. Same scenario and seed give deep-equal results (tested).
- Calls are synchronous RPCs: a request holds a worker while waiting on its dependencies, which is how a slow database exhausts its callers.
- Timeouts are scheduled at dispatch. On timeout the caller may retry, but the abandoned work keeps running (zombie work), which is a real cause of retry storms.
- Circuit breakers keep caller-side failure windows. Rate limiting is a token bucket at the entry, counting rejections separately.

Tests: `simulate/simulator.test.ts`. Read "cascades" and "amplifies load with retries" first.

## 5. What if?

`simulate/interventions.ts`.
- `modelAt(scenario, t)` replays scheduled changes to get the model at a moment.
- `branchScenario` compiles interventions into new scheduled changes at the decision time and returns plain-language assumptions. A rollback before its deploy removes the deploy entirely, and a rollback after it restores the previous parameters.
- `compareRuns` computes deltas and verdicts, and asserts the prefix is identical.

In the UI, `src/features/story/useWhatIf.ts` runs the baseline and branches in a Web Worker, and `FaultlineTimeline.tsx` draws the branch from the decision point.

## 6. Synthetic incidents that agree with themselves

`scenarios/definitions.ts` and `generate.ts`: each demo incident is a scenario run through the simulator, with its telemetry turned into logs, alerts and deploy events. Because the evidence is generated from the same model the what-if uses, the replay and the what-if baseline match. The story-beat tests in `reports.test.ts` check that the plain-language story matches what the simulation produced.

## 7. The platform layer

- `src/schemas/faultline-schemas.ts`: 18 collections. Team-scoped ones use `teamField` plus a `team_members` collection, so role checks happen on the server.
- `src/actions/index.ts`: server actions (create incident, register source, start, retry or cancel ingestion, copy demo, and so on). The acting user always comes from the verified session (the `userId` the platform passes to each action), and permissions are checked against it with `requireRole`. Ids in the payload only name a target. For example, `setMember` reads the member to change from `params.userId`, but only after confirming the caller is an owner.
- `src/jobs.ts` and `worker.ts`: the ingestion job room (2 attempts, 5 s backoff) and its stages (reading, validating, normalizing, deduplicating, correlating, persisting). Clients can neither enqueue nor read jobs directly. Progress is mirrored into a collection.
- `src/server/keys.ts`: the private-file key check, with exhaustive tests in `keys.test.ts`.
  The live platform stores `scope=self` uploads at `apps/<appId>/users/<userId>/<name>`, prefixed with the app **id**, not its name. This was confirmed by a real upload on 2026-11-26 and is pinned by a test.
- `src/server/actions.test.ts`: drives the real actions through an in-memory RecordRoom that enforces the schemas' `immutable` columns, plus the outsider, viewer, collaborator and revocation matrix. It exists because two bugs reached the live app that unit tests of pure helpers could not catch.

## 8. Two builds, one UI

`vite.config.ts` builds the DeepSpace app. `vite.vercel.config.ts` builds `src/vercel/` with `__FAULTLINE_TARGET__ = 'vercel'`: no auth providers, synthetic or browser-local data only, routes code-split. `src/lib/target.ts` decides which links exist. The standalone build never claims cloud features it doesn't have.

## 9. Worked example: adding an intervention

This change exists in the repository (commit `cfa83fa`), so you can walk through it file by file. Goal: a "Change timeout" what-if, setting how long a service waits for each downstream call.

**1. Write the tests first** (`packages/engine/src/simulate/simulator.test.ts`, the three `set_timeout` tests in the "counterfactual branches" block):

```ts
it('a timeout shorter than the dependency fails calls it used to complete', () => {
  const healthy = small()  // api -> db, db answers in ~10 ms
  const { scenario: b } = branchScenario(healthy, 30, [{ kind: 'set_timeout', service: 'api', timeoutMs: 2 }])
  const cmp = compareRuns(runSimulation(healthy), runSimulation(b), 30)
  expect(cmp.overall).toBe('worse')
})
```

The other two tests check that the change applies only after the branch point (`modelAt` at 29 s vs 31 s), states its assumption, keeps the prefix identical, and rejects out-of-range values and unknown services. Run `npm run test:engine` and watch all three fail.

**2. Extend the union** (`interventions.ts:14`):

```ts
| { kind: 'set_timeout'; service: string; timeoutMs: number }
```

**3. Give it a label, a description** (`INTERVENTION_KINDS`, line 25) **and a sentence** (`describeIntervention`, line 66).

**4. Compile it** (`branchScenario`, line 154):

```ts
case 'set_timeout': {
  if (!(iv.timeoutMs >= 1 && iv.timeoutMs <= 600_000)) throw new RangeError('Timeout must be within [1, 600000] ms.')
  const was = svc(iv.service).timeoutMs
  at({ kind: 'set_service', service: iv.service, patch: { timeoutMs: Math.round(iv.timeoutMs) } }, describeIntervention(iv))
  assumptions.push(`${iv.service} waits up to ... (was ${was} ms); calls already in flight keep their old deadline.`)
  break
}
```

Two details worth pointing out:
- `timeoutMs` is already in `SERVICE_PATCH_KEYS` (`util/safe.ts`), the allow-list the simulator uses when applying patches. A new parameter would need adding there, which is deliberate: patches can't set arbitrary keys.
- The assumption was checked against the simulator, not guessed. `simulator.ts:436` schedules each call's timeout when the call is dispatched, so in-flight calls really do keep their old deadline.

**5. Let the type checker find the UI.** `npx tsc --noEmit` failed on `defaultIntervention` in `src/features/simulate/InterventionEditor.tsx`, because its switch over every kind no longer returned for all of them. Add a default (the first service that calls something, at its current timeout) and the two editor fields.

**6. Verify.** `npm run test:engine` (103 passing, including a reproducibility test for the timeout branch added later), `npm run type-check`, `npm run lint`.
