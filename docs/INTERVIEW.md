# Interview guide

How to explain Faultline at three depths, where the interesting code lives, and a worked change you can walk through live. The section on AI assistance is honest about who wrote what; read it before you present the project as your own work.

## The 5-second version

> Faultline is a flight recorder for software: it replays an outage from its logs and lets you test what a different decision would have changed.

## The 30-second version

> When a site goes down, the clues are scattered across logs, deploy notes and alerts. Faultline imports that evidence, puts it on one timeline, and links events into likely cause-and-effect chains, ranked with the evidence behind each. Then you pick a moment, say "what if we had rolled back here?", and a deterministic simulator replays the incident from that point so you can compare outcomes side by side. It runs on DeepSpace (Cloudflare Workers and Durable Objects) with private uploads, background import jobs and shared workspaces. There's a no-account demo on Vercel.

## The technical version (2–3 minutes)

1. **Normalization** (`packages/engine/src/normalize/normalize.ts:148`, `normalizeSource`). Parses JSON, JSON lines, CSV, plain-text logs and OpenTelemetry exports into one canonical event shape. It redacts secrets and email addresses before anything is stored, deduplicates, and gives each event a stable id (`util/hash.ts:23`, a cyrb53 hash of its content), so re-importing the same file is idempotent.
2. **Correlation** (`correlate/correlate.ts:178`). Indexes events by service and time and only scores candidate pairs that are close in time and connected in the dependency graph, which avoids O(n²) comparisons. Each signal (shared trace, call-graph adjacency, type compatibility, and so on) has a weight, and they combine by **noisy-OR** (`correlate.ts:285`). Adding evidence can only raise a score, and no single weak signal dominates. The score then decays with the time gap (`exp(-Δt/τ)`). Edges only point forward in time, so the result is a DAG.
3. **Hypotheses** (`correlate/hypotheses.ts:104`). Candidate root causes (a deploy, a saturated resource, a timeout origin, retry amplification) ranked with the evidence behind each. They stay labeled *inferred* until a person confirms them, and the report never calls an unconfirmed cause the root cause.
4. **Replay** (`replay/replay.ts:176`, `ReplayEngine`). Events sit in a `Float64Array` of timestamps. Seeking is a binary search to the target time, then a pure reducer (`applyEvent`) runs forward from the nearest checkpoint (one every 256 events). Scrubbing the timeline costs about log n plus at most 256 steps, not a full re-scan.
5. **Simulation** (`simulate/simulator.ts:227`, `runSimulation`). A discrete-event simulator: a binary heap ordered by `(time, sequence)` (`simulate/heap.ts:11`), so ties are broken by insertion order and runs are reproducible. Randomness comes only from a seeded `sfc32` generator (`util/rng.ts:8`). It models queues, worker capacity, timeouts, retries with backoff and jitter, circuit breakers, rate limits, and "zombie" work that keeps running after the caller gave up.
6. **What-if branches** (`simulate/interventions.ts`). An intervention compiles into scheduled model changes at the decision time, plus a plain-language assumption. `compareRuns` (`interventions.ts:209`) checks that the branch's samples before the decision are byte-identical to the baseline (`prefixIdentical`). If they differ, something is wrong with the comparison itself.
7. **Platform.** DeepSpace collections enforce roles on the server (`src/schemas/faultline-schemas.ts`). Imports are background jobs with retries (`src/jobs.ts`, `worker.ts`). Uploaded files live in per-user private storage, and every server path that touches a file key re-checks it against the anchored prefix `apps/<appId>/users/<userId>/` (`src/server/keys.ts:22`, used at `src/actions/index.ts:162` and `:188`).

## Questions you should expect

**"How do you know the simulator isn't just telling you what you want to hear?"** Three things. The demo incidents were generated by the same simulator, so baseline and branch use one model. The prefix-identical check proves the branch only differs after the decision. And there are tests where interventions must come out *worse*: shrinking a pool to one connection, or a timeout shorter than the dependency's response time (`simulate/simulator.test.ts`, "reports an intervention that makes things worse honestly" and "a timeout shorter than the dependency fails calls it used to complete").

**"Are the correlation scores probabilities?"** No. They're heuristic scores in [0, 1] that have not been calibrated against labeled incidents. The UI and the docs say so (`docs/CORRELATION.md`, `docs/TRADEOFFS.md`).

**"What would you do with real production data?"** Calibrate the signal weights against labeled incidents, add trace-context propagation as a first-class signal, and fit the derived system model's capacities from observed latency instead of defaults (the model already discloses which values were assumed).

**"What was the hardest bug?"** The private-file check. It started as a substring match on the storage key, which a crafted key could satisfy. It's now an anchored prefix check that also rejects encoded and double-encoded separators, Unicode slash look-alikes, control characters, traversal and empty segments, and refuses anything that changes under NFKC normalization. `src/server/keys.test.ts` covers each case. The original issue was never tested against the live platform, so it shouldn't be described as "unexploitable".

**"Why a discrete-event simulator and not a formula?"** Queueing formulas assume steady state. Outages are about transitions: a deploy lands, queues fill, retries multiply the load, breakers open, the system recovers or doesn't. Simulating each request through those mechanisms captures the feedback loops that make cascades.

## Worked example: adding an intervention

This change exists in the repository (commit `cfa83fa`), so you can walk through it file by file. Goal: a "Change timeout" what-if, setting how long a service waits for each downstream call.

**1. Write the tests first** (`packages/engine/src/simulate/simulator.test.ts`, the three `set_timeout` tests in the "counterfactual branches" block):

```ts
it('a timeout shorter than the dependency fails calls it used to complete', () => {
  const healthy = small()  // api -> db, db answers in ~10 ms
  const { scenario: b } = branchScenario(healthy, 30, [{ kind: 'set_timeout', service: 'api', timeoutMs: 2 }])
  const cmp = compareRuns(runSimulation(healthy), runSimulation(b), 30)
  expect(cmp.overall).toBe('worse')
})
```

The other two tests check that the change applies only after the branch point (`modelAt` at 29 s vs 31 s), states its assumption, keeps the prefix identical, and rejects out-of-range values and unknown services. Run `npm run test:engine` and watch all three fail.

**2. Extend the union** (`interventions.ts:14`):

```ts
| { kind: 'set_timeout'; service: string; timeoutMs: number }
```

**3. Give it a label, a description** (`INTERVENTION_KINDS`, line 25) **and a sentence** (`describeIntervention`, line 66).

**4. Compile it** (`branchScenario`, line 154):

```ts
case 'set_timeout': {
  if (!(iv.timeoutMs >= 1 && iv.timeoutMs <= 600_000)) throw new RangeError('Timeout must be within [1, 600000] ms.')
  const was = svc(iv.service).timeoutMs
  at({ kind: 'set_service', service: iv.service, patch: { timeoutMs: Math.round(iv.timeoutMs) } }, describeIntervention(iv))
  assumptions.push(`${iv.service} waits up to ... (was ${was} ms); calls already in flight keep their old deadline.`)
  break
}
```

Two details worth pointing out:
- `timeoutMs` is already in `SERVICE_PATCH_KEYS` (`util/safe.ts`), the allow-list the simulator uses when applying patches. A new parameter would need adding there, which is deliberate: patches can't set arbitrary keys.
- The assumption was checked against the simulator, not guessed. `simulator.ts:436` schedules each call's timeout when the call is dispatched, so in-flight calls really do keep their old deadline.

**5. Let the type checker find the UI.** `npx tsc --noEmit` failed on `defaultIntervention` in `src/features/simulate/InterventionEditor.tsx`, because its switch over every kind no longer returned for all of them. Add a default (the first service that calls something, at its current timeout) and the two editor fields.

**6. Verify.** `npm run test:engine` (102 passing), `npm run type-check`, `npm run lint`.

## How AI was used, and how to talk about it

All of the code and documentation in this repository was written by an AI coding agent (Claude Code), working in the repository from detailed written briefs by the owner. Details are in [AGENT-CONTRIBUTIONS.md](AGENT-CONTRIBUTIONS.md).

Be accurate in an interview:
- Say you directed the project and wrote the product brief, and describe the AI's role plainly.
- Only claim to have personally reviewed, tested or understood the parts you actually have. [HUMAN-VERIFICATION.md](HUMAN-VERIFICATION.md) is a checklist for doing that review. Working through it, and making a change like the worked example yourself, is the honest way to be able to explain this code.
- Don't present the demo incidents as real outages, or the correlation scores as calibrated.
