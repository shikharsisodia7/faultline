## Project

**Faultline**: the flight recorder for software.

- Live on DeepSpace: https://faultline.app.space
- Source: https://github.com/shikharsisodia7/faultline
- No-account demo (Vercel): https://faultline-coral.vercel.app

## What it does

Faultline replays a software failure from its logs and lets you explore what a different decision would have changed. You import logs or traces. Faultline normalizes them, removes secrets, builds a timeline, and links events into ranked, explained possible causes, labeled *inferred* until a person confirms them. You then pick a moment and a decision (roll back, add capacity, retry less, rate limit, change a timeout), and a seeded discrete-event simulator replays the incident from that point. The original and the alternative are compared side by side, and a decision that would have made things worse is shown as worse.

## Why this project

Postmortems usually explain what happened but rarely let you test the alternatives people argue about afterwards. Faultline makes those alternatives concrete, while staying honest about what is observed, what is inferred, and what is simulated.

## DeepSpace integrations (verified working on the live app)

1. **Authentication.** OAuth sign-in. Every server action rejects anonymous and forged tokens.
2. **RecordRoom persistence and real-time sync.** Incidents, events, hypotheses and reviews persist and sync between sessions within seconds.
3. **R2 file storage (`scope: self`).** Evidence is stored privately per user. The server re-validates every file key against the exact owner prefix before using it.
4. **JobRoom background jobs.** Imports run as staged, retryable jobs that outlive the request.
5. **Server-enforced permissions.** Team-scoped collections plus server actions that check the caller's role (owner, collaborator, viewer).
6. **Deployment.** One-command deploys from the GitHub source.

The integration-proxy features (AI summary, GitHub commit import, web search) are implemented but off by default, because they are billed to the owner's credits. They are not claimed as verified.

## The most important tradeoff

**A simplified model, used honestly, over a realistic model used vaguely.** The simulator models queues, worker capacity, timeouts, retries, breakers and rate limits, but not real hardware or real traffic. The cost: results are estimates, not predictions. The benefit: every run is reproducible (seeded, deterministic event ordering), every run lists its assumptions, and branches are checked to be identical to the baseline before the decision point. The demo incidents are generated by the same model, so their what-if results agree with their logs.

## Limitations

- The live three-account authorization suite is written but has not run yet: it needs DeepSpace test accounts created by the owner.
- Two app credentials were exposed in private Vercel deployment sources (never public, never in git). Those deployments are deleted, and revocation has been requested from DeepSpace; it is not yet confirmed.
- Correlation scores are heuristic, not calibrated probabilities.
- Simulations of imported incidents use a derived model with default parameters where the logs don't say otherwise; those defaults are disclosed in each run.
- Demo incidents are synthetic and labeled.
- No usability testing with real people has happened yet.
